# Monitoring: Prometheus + Grafana

`scripts/dev.sh` starts both with the rest of the stack.

| What | Where |
|------|-------|
| Dashboards | http://localhost:8484 → *Dashboards → TenaShop* (no sign-in needed to view) |
| Alerts | http://localhost:9390/alerts, also listed in Grafana → *Alerting* |
| Alert emails | Alertmanager http://localhost:9393 sends them; they land in Mailpit http://localhost:8626 |
| Raw metrics | `curl http://localhost:8181/actuator/prometheus` (only from this machine) |

Prometheus scrapes the backend every 15 s at `host.docker.internal:8181/actuator/prometheus`. The endpoint answers only direct requests from this machine or the Docker network. Requests through ngrok or the nginx frontend carry `X-Forwarded-For` and are refused (403), so metrics never leak to the internet.

```
backend /actuator/prometheus ──┐
blackbox (outside checks) ─────┼─► Prometheus :9390 ──► alerts.yml ──► Alertmanager :9393 ──► email (Mailpit)
                               │         ▲
Postgres (grafana_reader) ─────┼─────────┴──────────── Grafana :8484 (dashboards, Alerting, silences)
```

## Dashboards

Every dashboard links to the others (top right) and shows two kinds of markers on its charts: **Backend restarts** (orange) and **Alerts firing** (red). Toggle them at the top.

| Dashboard | Shows |
|-----------|-------|
| **Business** (SQL) | Revenue, paid orders, average order, checkout conversion, refunds, discounts; revenue and orders over time; top products; paid by method; why payments did not go through; to fulfil now, oldest waiting, on the way, paid → delivered; low stock; latest orders (click to open in admin); customer emails, stored webhooks, failed sign-ins, discount codes. Dropdowns: **BillPay** (All / Sandbox / Live) and **Group by** (hour / day / week) |
| **Uptime & Alerts** | Firing and pending alerts, active alert list, Alertmanager status; each endpoint UP/DOWN now and over time, availability %, response time, TLS certificate expiry |
| **Payments** | Success rate, paid, payment links created, orders expired; payments by outcome over time; failed tries by reason (INSUFFICIENT_FUNDS, CUSTOMER_DECLINED, ...); paid by method; BillPay latency (p50/p95) and calls by outcome; BillPay error rate; refunds |
| **Webhooks & Kafka** | Accepted / duplicate / rejected deliveries; received → processed delay; signature failures; Kafka consumer lag, messages consumed and produced |
| **App** | Backend up, uptime, requests/s, 5xx share, heap; HTTP by status; slowest endpoints; JVM heap, CPU, DB pool, threads and GC |

The dashboards are files in [monitoring/grafana/dashboards](../monitoring/grafana/dashboards), generated by [generate-dashboards.mjs](../monitoring/grafana/generate-dashboards.mjs). To change one, edit the script and run `node monitoring/grafana/generate-dashboards.mjs`. Grafana picks up the change within a few seconds. Edits made in the Grafana UI are not saved.

### Business dashboard and customer data
It reads the shop database as **grafana_reader**, a read-only user created by the one-shot `grafana-db-init` service from [grafana-reader.sql](../monitoring/postgres/grafana-reader.sql) on every `docker compose up`. It can only read the columns listed in that file: no customer names, phones, emails, addresses, password hashes or BillPay payloads, because anyone who can open Grafana could query the data source. Queries time out after 15 s. To show a new column, add it to the list and run `docker compose up -d grafana-db-init`. Numbers here come from the database, so unlike Prometheus counters they survive backend restarts.

## Outside checks (blackbox exporter)
Every 30 s, [blackbox.yml](../monitoring/blackbox/blackbox.yml) checks the endpoints listed in [prometheus.yml](../monitoring/prometheus/prometheus.yml) (job `probes`): the store, backend health, the **ngrok tunnel** BillPay calls, and the BillPay sandbox API (any answer, even 401, counts as up). It runs on the host network (port 9395) so it sees `localhost` exactly like your browser. If your ngrok domain changes, update the tunnel target there.

## Alerts ([alerts.yml](../monitoring/prometheus/alerts.yml))

| Alert | Fires when |
|-------|-----------|
| BackendDown | Prometheus can't scrape the backend for 1 min |
| NoSuccessfulPayment | Payment links were created in the last 30 min but none was paid |
| BillPayErrorRateHigh | More than 10% of BillPay calls fail (5xx or unreachable) for 5 min |
| WebhookSignatureFailures | Any webhook failed the HMAC check in the last 10 min |
| WebhookProcessingSlow | p95 webhook received → processed above 30 s for 5 min |
| KafkaConsumerLagGrowing | More than 50 messages waiting on a topic for 5 min |
| HighServerErrorRate | More than 5% of backend requests answer 5xx for 5 min |
| PaymentDeclineSpike | 5 or more tries declined with the same reason in 10 min |
| DatabasePoolExhausted | Requests waiting for a DB connection for 2 min |
| JvmHeapHigh | Heap above 90% for 10 min |
| EndpointDown | An outside check (store, backend, ngrok tunnel, BillPay) failed for 2 min |
| TlsCertificateExpiringSoon | A checked https certificate expires within 14 days |

### Notifications
Prometheus sends firing alerts to **Alertmanager** ([alertmanager.yml](../monitoring/alertmanager/alertmanager.yml)), which emails `ops@tenashop.local` through Mailpit: one email per alert name, a reminder every 4 h (1 h for critical), and a "resolved" email when it clears. While **BackendDown** fires, the alerts it causes (no payments, Kafka lag, tunnel down, ...) are held back so you get one email, not five.

- **Silence** an alert (maintenance, known BillPay outage): Grafana → *Alerting → Silences* (choose Alertmanager), or http://localhost:9393.
- **Test** the email path: `curl -XPOST -H 'Content-Type: application/json' localhost:9393/api/v2/alerts -d '[{"labels":{"alertname":"MonitoringTest","severity":"warning"}}]'`, then check Mailpit.
- **Go-live:** point `smtp_*` at a real SMTP server and change `to:`, or enable the Telegram receiver in the file. Reload with `curl -XPOST localhost:9393/-/reload`.
- After editing `alerts.yml` or `prometheus.yml`: `curl -XPOST localhost:9390/-/reload`.

## TenaShop metrics

| Metric | Labels |
|--------|--------|
| `tenashop_payments_requested_total` | `result` = created / rejected / error |
| `tenashop_payments_status_total` | `status` = SUCCEEDED / FAILED / EXPIRED / CANCELLED / ... |
| `tenashop_payments_paid_total` | `method` (TEST_WALLET, ...) |
| `tenashop_payments_failed_total` | `reason` |
| `tenashop_payments_tries_failed_total` | `reason`: failed tries on a payment BillPay kept open |
| `tenashop_billpay_requests_seconds_*` | `operation` (create_payment, get_payment, create_refund), `outcome` (2xx / 4xx / 5xx / network) |
| `tenashop_webhooks_received_total` | `result` = accepted / duplicate / rejected_signature / invalid_json |
| `tenashop_webhooks_processing_delay_seconds_*` | `status` = PROCESSED / DUPLICATE / IGNORED |
| `tenashop_orders_status_total` | `status` |
| `tenashop_refunds_status_total` | `status` |

Counters are created at 0 when the backend starts, so `increase()` over a time range counts the first event too. Counters tied to the database are only incremented after the transaction commits.
