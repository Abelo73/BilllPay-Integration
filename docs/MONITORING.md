# Monitoring: Prometheus + Grafana

`scripts/dev.sh` starts both with the rest of the stack.

| What | Where |
|------|-------|
| Dashboards | http://localhost:3300 → *Dashboards → TenaShop* (no sign-in needed to view) |
| Alerts | http://localhost:9390/alerts, also listed in Grafana → *Alerting* |
| Raw metrics | `curl http://localhost:8181/actuator/prometheus` (only from this machine) |

Prometheus scrapes the backend every 15 s at `host.docker.internal:8181/actuator/prometheus`. The endpoint answers only direct requests from this machine or the Docker network. Requests through ngrok or the nginx frontend carry `X-Forwarded-For` and are refused (403), so metrics never leak to the internet.

## Dashboards

| Dashboard | Shows |
|-----------|-------|
| **Payments** | Success rate, paid, payment links created, orders expired; payments by outcome over time; failed tries by reason (INSUFFICIENT_FUNDS, CUSTOMER_DECLINED, ...); paid by method; BillPay latency (p50/p95) and calls by outcome; BillPay error rate; refunds |
| **Webhooks & Kafka** | Accepted / duplicate / rejected deliveries; received → processed delay; signature failures; Kafka consumer lag, messages consumed and produced |
| **App** | Backend up, uptime, requests/s, 5xx share, heap; HTTP by status; slowest endpoints; JVM heap, CPU, DB pool, threads and GC |

The dashboards are files in [monitoring/grafana/dashboards](../monitoring/grafana/dashboards), generated by [generate-dashboards.mjs](../monitoring/grafana/generate-dashboards.mjs). To change one, edit the script and run `node monitoring/grafana/generate-dashboards.mjs`. Grafana picks up the change within a few seconds. Edits made in the Grafana UI are not saved.

## Alerts ([alerts.yml](../monitoring/prometheus/alerts.yml))

| Alert | Fires when |
|-------|-----------|
| BackendDown | Prometheus can't scrape the backend for 1 min |
| NoSuccessfulPayment | Payment links were created in the last 30 min but none was paid |
| BillPayErrorRateHigh | More than 10% of BillPay calls fail (5xx or unreachable) for 5 min |
| WebhookSignatureFailures | Any webhook failed the HMAC check in the last 10 min |
| WebhookProcessingSlow | p95 webhook received → processed above 30 s for 5 min |
| KafkaConsumerLagGrowing | More than 50 messages waiting on a topic for 5 min |

Alerts are visible in Prometheus and Grafana. Sending them to email, Telegram or Slack needs Alertmanager, which is planned for go-live (P7).

## TenaShop metrics

| Metric | Labels |
|--------|--------|
| `tenashop_payments_requested_total` | `result` = created / rejected / error |
| `tenashop_payments_status_total` | `status` = SUCCEEDED / FAILED / EXPIRED / CANCELLED / ... |
| `tenashop_payments_paid_total` | `method` (TEST_WALLET, ...) |
| `tenashop_payments_failed_total` | `reason` |
| `tenashop_payments_tries_failed_total` | `reason`: failed tries on a payment BillPay kept open |
| `tenashop_billpay_requests_seconds_*` | `operation` (create_payment, get_payment, create_refund), `outcome` (2xx / 4xx / 5xx / network) |
| `tenashop_webhooks_received_total` | `result` = accepted / duplicate / rejected_signature / invalid_json |
| `tenashop_webhooks_processing_delay_seconds_*` | `status` = PROCESSED / DUPLICATE / IGNORED |
| `tenashop_orders_status_total` | `status` |
| `tenashop_refunds_status_total` | `status` |

Counters are created at 0 when the backend starts, so `increase()` over a time range counts the first event too. Counters tied to the database are only incremented after the transaction commits.
